# v0.3.16 — Discovery Run Guard Shell

## Summary

Adds a thread-safe run guard to `POST /api/v1/discovery/trigger` that prevents concurrent discovery runs. A second call while a run is in progress returns HTTP 409. The guard is stored on `app.state` and initialised at startup.

## Changes

| File | Change |
|------|--------|
| `backend/app/core/run_guard.py` | New file — `DiscoveryRunGuard` (threading.Lock wrapper) |
| `backend/app/main.py` | Attach `DiscoveryRunGuard` instance to `app.state.discovery_run_guard` at startup |
| `backend/app/api/discovery.py` | Acquire guard before run; release in finally; HTTP 409 if already locked |
| `backend/tests/api/test_discovery_api.py` | 3 new run guard tests |

## Guard Behaviour

| Condition | Result |
|-----------|--------|
| No run in progress | Lock acquired, chain runs normally |
| Run already in progress | HTTP 409 — Discovery run already in progress |
| Run completes (success or error) | Lock always released via finally |

## Design Decisions

- `threading.Lock` with `blocking=False` — non-blocking acquire; immediate 409 on contention
- Guard stored on `app.state` — single instance per app lifetime, accessible from request context
- `try/finally` in endpoint — lock released even when HTTP exceptions are raised
- HTTP 409 Conflict — semantically correct for "resource busy / try again later"
