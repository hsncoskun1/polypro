# v0.4.1 — Rule Governance + Visibility Pack

## Summary

Introduces the rule governance and visibility layer on top of the v0.4.0 trading decision foundation. Admin controls which rules are available, visible, editable, required, or locked. Users interact only within what policy permits. No UI in this version — data model is UI-ready.

## Governance Model

| Concept | Meaning |
|---------|---------|
| `available` | Admin makes rule available in system |
| `visible` | Rule appears in user panel |
| `editable` | User can toggle enabled state |
| `required` | User cannot disable (always on) |
| `locked_by_admin` | Governance seam from v0.4.0 — not a blocking state |
| `default_enabled` | Authoritative state for non-editable rules |
| `min_active_rules` | Minimum number of active rules enforced by policy |
| `max_active_rules` | Maximum number of active rules enforced by policy |

## Rule Telemetry Fields

| Field | Description |
|-------|-------------|
| `rule_name` | Identifies the rule |
| `visible` | Whether rule is shown in user panel |
| `editable` | Whether user can toggle it |
| `enabled` | Resolved enabled state (policy + selection) |
| `locked_by_admin` | Admin lock state |
| `state` | Live rule state from EntryDecision (pass/fail/disabled/etc.) |
| `current_value` | Actual measured value |
| `threshold_value` | Threshold being compared against |
| `distance_to_trigger` | How far from triggering |
| `reason` | Human-readable fail reason |

## Governance Rules (Sabit Kararlar)

1. Admin determines which rules are available in system
2. User can only enable/disable rules admin permits
3. Non-editable rules use policy `default_enabled` — user selection ignored
4. Required rules are always enabled regardless of user selection
5. `disabled` does not count as pass
6. `locked_by_admin` is not a blocking state (v0.4.0 semantics preserved)
7. Hidden rules excluded from telemetry
8. Runtime state not directly edited — config derived from policy
