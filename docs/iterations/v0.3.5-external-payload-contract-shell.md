# Iteration Notes — v0.3.5 External Payload Contract Shell

## Goal

Establish a named boundary between the external world (Polymarket API) and the internal adapter layer. When real HTTP integration arrives, only `PolymarketMarketPayload` field names change — mapping logic and all downstream layers remain untouched.

## Decisions

- **`PolymarketMarketPayload` in `adapters/external_payload.py`**: Separate from `RawPayloadItem`. `RawPayloadItem` is the adapter's internal input; `PolymarketMarketPayload` is the external format shell. Two types = two clear seam points.
- **Field names approximate Polymarket**: `condition_id`, `question`, `end_date` — close enough to real Polymarket API shape to be meaningful, not so specific that they break before real integration.
- **`ExternalPayloadMappingError`**: Dedicated exception — makes mapping failures distinguishable from normalization failures (`NormalizationError`) and pipeline failures (`TypeError`). No silent fallback.
- **Whitespace stripped in mapper**: Same pattern as `normalize_item()`. Caller sends raw string; mapper owns cleanup.
- **No wiring to trigger endpoint**: External payload mapping is independently testable. Wiring it to an HTTP fetch path is a future step.
