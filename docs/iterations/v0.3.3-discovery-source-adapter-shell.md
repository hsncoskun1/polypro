# Iteration Notes — v0.3.3 Discovery Source Adapter Shell

## Goal

Establish the seam point between the discovery pipeline and future external source integration. The adapter is the only thing that will change when real Polymarket HTTP fetching is added — pipeline, service, and API layers remain untouched.

## Decisions

- **New `backend/app/adapters/` package**: Separate from `domain/` — adapters translate external formats into domain types. Not orchestration (services/) and not domain logic.
- **`RawPayloadItem` dataclass**: Separate type from `RawMarketItem`. Marks where external format ends and domain format begins. Fields match `RawMarketItem` for now; will diverge when real Polymarket field names are known.
- **`PayloadDiscoveryAdapter` implements `RawDiscoverySource` structurally**: No explicit `Protocol` inheritance needed — duck-typed via `.fetch() -> list[RawMarketItem]`.
- **No injection into existing endpoint**: Trigger endpoint still uses `StubRawDiscoverySource` from request body. Adapter is independently testable — wiring it to the endpoint is a future step.
- **Adapter tested directly and through service**: Both unit-level (adapter.fetch()) and integration-level (run_discovery_service with adapter) tests written.
