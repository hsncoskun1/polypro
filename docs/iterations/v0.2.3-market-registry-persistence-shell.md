# Iteration Notes — v0.2.3 Market Registry Persistence Shell

## Goal

Add a SQLite persistence layer so market registry state survives server restarts.

## Decisions

- **`SqliteMarketStore`** uses stdlib `sqlite3` only — no ORM, no migration system, no abstraction beyond what the task requires.
- Table schema: `markets (market_id TEXT PRIMARY KEY, title TEXT, timeframe TEXT, status TEXT)`.
- **`save()` strategy**: DELETE all + INSERT all in a single transaction — simple full replacement, no partial updates.
- **`MARKET_STORE_PATH`** env var controls DB file location; defaults to `data/markets.db`. Test isolation uses `tmp_path` fixture.
- **Store integrated in lifespan** (`app.main`): on startup, load DB → hydrate registry. On mutation (POST, PATCH), save registry to DB.
- **No background sync** — save is synchronous and immediate on every write operation.
- **API test fixture updated**: `client(tmp_path)` sets `MARKET_STORE_PATH` to a `.db` file so each test gets an isolated SQLite DB and a fresh registry.

## Test Coverage

7 unit tests for `SqliteMarketStore`:
- load: empty on new DB, saved markets, inactive status, multiple markets
- save: creates parent dirs, overwrites previous, clears on empty list

1 integration test:
- `test_market_persists_across_restart`: two separate `TestClient` context managers against the same DB — confirms market created in session 1 is visible in session 2.

## Risk

- SQLite concurrent write access is limited by file locking. For single-process usage this is fine; would be a concern under multi-worker deployment. Acceptable for this stage.
